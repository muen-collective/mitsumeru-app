# Mitsumeru 0.2.6-dev

Internal build — carries the `-dev` suffix; the update channel is `dev`.

Wraps DeepSeek Harness **0.2.1-rc.2** (0.2.5 carried 0.2.1-alpha.2; rc.2 shipped 2026-10-17). The
pin is the only thing that had to change to wrap it — the harness version is data, not code. An rc pin
never ships to `latest`, so this build stays on the `dev` channel deliberately.

## What changed

- **DSH desktop parity — the rail now collapses all the way to zero** (founder, 2026-10-12:
  *"i want full parity"*, after *"dsh left rail collapse all the way, this is the design I always
  wanted"*). The shell now marks the document `<html data-platform=darwin>`, which is the single
  attribute the harness reads to switch three behaviours at once:
  - the collapsed sidebar's width becomes `darwin ? 0 : 56`, so a closed rail leaves **nothing** on
    the left instead of a 56px icon column (`ui-layout`);
  - the desktop chrome turns on — `[data-window-drag]` regions, the translucent New-session button,
    the sidebar gradient;
  - the **native keyboard bridge** becomes mandatory: with the mark set, `dsh-client-shortcuts`
    throws `Desktop keyboard bridge unavailable` unless `window.dshDesktop.keyboard` exists, and the
    frame does not mount at all.
- **The native keyboard bridge is real, not a stub.** In desktop runtime the DOM key path serves only
  fixed actions, so the configurable bindings must arrive over IPC. The main process imports the
  harness's own published domain module (`@deepseek-ai/dsh-client-shortcuts/protocol`) to resolve the
  binding table, claims registered chords on `before-input-event`, and delivers them to the page.
  Preferences persist at `<stateDir>/keybindings.json`.
- **Window chrome**: `titleBarStyle: hiddenInset` with `trafficLightPosition {x:16, y:18}`,
  `vibrancy: 'sidebar'` and a transparent background — the official shell's own darwin values. The
  vibrancy matters: under the mark the harness's frame is `background: 0 0` and its sidebar is a
  `color-mix(…, transparent)` gradient, so a native material has to sit behind it.
- **Safety**: the preload marks the document only when the bridge is confirmed live, so if the
  protocol module cannot load the app degrades to the previous behaviour (56px rail, working app)
  rather than a dead boot. The previous session's `rail-collapse.ts` injection stays as the fallback.

## Fixed after the first parity build (same day, founder's eyes)

- **The colour was off.** The native material behind the sidebar followed the OS appearance while the
  app ran its own theme, so a light app on a dark system translated a dark grey panel behind a light
  UI. The shell now mirrors the harness's theme source (`html[data-ds-theme-source]`, `system` |
  `light` | `dark`, written by `ui-layout`) into Electron's `nativeTheme.themeSource`, which fixes the
  material, the window chrome and renderer `prefers-color-scheme` in one step. Fullscreen is mirrored
  the same way, so the harness's 48px title-band clearance and the hidden traffic lights agree.
- **"If I click settings, another menu pops up top left."** Our Muen account overlay (Epic 92) hid the
  stock settings rail and then *clicked the hidden launcher button*. A hidden element measures `0x0`,
  so anything anchored to it opens clamped at the window's top-left. Root cause, read from the
  harness's own source: the `settings.launcher` slot is filled by `AccountMenu` — that launcher **is**
  the account menu's anchor, which is why the stray panel was the account menu (Settings / Feedback /
  Sign in). The overlay now opens Settings through the harness's **command path** instead —
  `{kind:'menu', commandId:'settings.open'}` over the bridge, the same mechanism the official shell
  drives its File menu with — which involves no DOM anchor and no key gesture at all.

## Fixed at the founder's review (same day, later)

- **The avatar's Language menu listed two languages, not the catalog** (founder, 2026-10-12: *"the
  language switcher from avatar only show zh, en, needs full set from language switcher"*). The menu
  carried a hardcoded `en`/`zh` pair whose comment said it was the harness's shipped catalog — true,
  and exactly why it was wrong: the other five languages arrive from `@muen/dsh-localize` through
  the runtime's `addLanguage`, and this menu was the one place the catalog never reached. It now reads
  `<html data-muen-languages="[{id,label}]">` — the mirror that plugin publishes, in the runtime's own
  order — and falls back to the built-in pair when nothing published one (a stock DSH, or a profile
  without the plugin). The rows are rebuilt **on open**, not at inject time, because the overlay is
  injected as the app boots, before any plugin has offered its languages.

## The update strip is gone (2026-10-20)

- **The banner across the top of the window became a pill beside the account row.** A full-width strip
  took permanent screen space to say something true for about a minute, and it sat in the window chrome
  rather than the account area where app-level actions live. It is replaced by what DSH Desktop does: a
  small button — 14px glyph + label — injected into the avatar row, drawn only while there is something
  to say. The glyph carries the phase (download arrow when available, spinner while checking /
  downloading / verifying, check when downloaded, dot on error) and the click does what the phase
  implies: **Restart** when downloaded, **Retry** on error, **Release notes** when available, nothing
  while busy. The *visibility* rules carry over from the banner unchanged — `checking` and `current`
  only appear when a person asked, `error` only when they asked or when an update was already in
  flight — because that reasoning was about not interrupting someone, not about where the thing is
  drawn. `update-banner.ts` is deleted; `update-indicator.ts` replaces it.
- **A 100% download is not "done".** electron-updater still verifies and unpacks after the last byte,
  and the old progress bar sat frozen at 100% through that gap. `verifying` is a state now, so the pill
  says what is happening instead of looking stuck.
- **A version already handed to `quitAndInstall` is not offered again on the next check** (founder,
  2026-10-19: *"when I restarted it did the update banner again"*). After the relaunch the on-disk
  version may not have changed yet, so the same version came back as *available*; the updater now
  remembers what it asked Squirrel to install and reports `current` instead.
- **The account row spans the sidebar** instead of floating as a pill: it reads the sidebar column's
  live box, follows a resize, reserves its own height at the foot of the rail so content scrolls above
  it, and hides when the rail collapses to zero — it lives inside the rail, so it goes with it. It is
  **transparent, not a token fill**: on macOS the sidebar paints a gradient plus a `color-mix` over
  `--dsw-specific-sidebar-fill`, so any flat copy of that token leaves a visible seam along the row's
  top edge. The row is a `<button>`, so the UA's outset border had to be reset — that border was the
  white line it wore.
- **No leading seat was built, deliberately.** DSH's sidebar toggle and New Session buttons are its own
  `HeaderLeadingControls`, mounted by `AppFrame` when `darwin && sidebarCollapsed`. This shell already
  sets `data-platform`, so they were mounting all along; an injected copy only stacked a second pair on
  top of them. The native pair keeps its own icons, tooltips and React handlers.

## Gates

This cut was made with `pnpm release:cut`, which stops at the first failure and never publishes. Every
step below ran, in order, on the artifacts that are attached to this release:

- `check:label`, `check:identity`, `typecheck` — clean.
- `package:mac` — both arches built and signed with **Developer ID Application: THUY QUANG PHAM
  (4Q6GC57QG4)**, each carrying a secure timestamp.
- `notarize:all` — **8 submissions accepted** by Apple's notary service (app bundle + final dmg, per
  arch), each stapled, and every `staple and validate` reported *worked*. Gatekeeper accepts them.
- `smoke` — **5/5**: harness readiness line, UI loaded, clean quit, no orphan harness, app exited.
- `smoke:native` — the native surfaces against the packaged app.
- `verify:surfaces`, `verify:mount`, `verify:release` — all green, including the mount probe reading the
  served bundle and the frame's own seats.
- `verify:artifacts` — **20/20**: each dmg/zip carries its own arch's addon and not the other's, and the
  Windows NSIS payload is x86-64 with the win32-x64 addon and every shipped `@muen` plugin.
- `verify:docs` — *"docs agree with the code"*.

Two gates failed first and were fixed rather than waived, because both were the gate's fault and not the
build's:

- **`smoke` blocked on a Keychain prompt.** It shared `userData` with the installed app, so it read that
  app's stored Muen session and called `safeStorage.decryptString` on it — which macOS gates behind a
  dialog. It sat at `auth-protocol-registered` for its whole 90s budget with the code fine. Smoke now
  runs on a throwaway profile: nothing to decrypt, nothing to ask.
- **`verify:artifacts` wanted 7 `@muen` plugins.** Two retired on 2026-10-02 and the assertion never
  moved, so it failed a correct payload. It now reads the expected set out of `SHIPPED_PLUGINS` and
  compares by name. Mutation-tested.

`dsh-localize`'s own suites were green at the parity session: `verify/catalog.mjs` 29/29, `mount` 37/37,
`overlay` 73/73, `memory` 36/36, `review` 21/21.

The rig's `menu-test.mjs` — the account menu and the language catalog, which had not been run since the
parity session — now passes against this build: **exit 0**, five screenshots, driven over CDP against
the packaged app with a mock-auth sign-in.

- The menu draws the harness's **catalog**, 8 languages — `zh, en, zh-TW, ja, ko, fr, de, es` — matching
  `<html data-muen-languages>` row for row, with English checked.
- Switching to 中文 flips `html lang` to `zh-CN` and localizes all three menu labels (设置 / 语言 /
  退出登录); switching back restores English.
- Sign out clears the session and returns the window to the sign-in page.

Running it needed three fixes to the test itself, all recorded there: it clicked Language by ordinal
position (Settings is appended first, so it opened Settings), it expected the signed-in row to read
"Signed in to Muen" (the row has shown the account name since 2026-10-02), and it assumed it started in
English (the choice persists). The language row also gained a stable `mua-lang` hook so the test stops
depending on order.

## Install

- Download the `.dmg` for your Mac: **arm64** for Apple silicon, the plain `Mitsumeru-0.2.6-dev.dmg`
  for Intel. Both are Developer-ID signed, notarized and stapled, so a downloaded copy opens without
  the Gatekeeper detour.
- Windows: `Mitsumeru-Setup-0.2.6-dev.exe` (x64, NSIS, not code-signed — SmartScreen may ask once).
- Local internal build: `pnpm package:dir`, then replace `/Applications/Mitsumeru.app` from
  `release/mac-arm64/Mitsumeru.app`.

This is a `-dev` build on the `dev` channel. It will not be offered to anyone running 0.2.5, because an
rc pin never ships to `latest`.
