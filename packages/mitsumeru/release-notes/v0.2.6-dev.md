# Mitsumeru 0.2.6-dev

Internal build — carries the `-dev` suffix; the update channel is `dev`.

Wraps DeepSeek Harness 0.2.1-alpha.2 (unchanged from 0.2.5).

## What changed

- **DSH desktop parity — the rail now collapses all the way to zero** (founder, 2026-10-12:
  *"i want full parity"*, after *"dsh left rail collapse all the way, this is the design I always
  wanted"*). The shell now marks the document `<html data-platform=darwin>`, which is the single
  attribute the harness reads to switch three behaviours at once:
  - the collapsed sidebar's width becomes `darwin ? 0 : 56`, so a closed rail leaves **nothing** on
    the left instead of a 56px icon column (`ui-layout`);
  - the desktop chrome turns on — `[data-window-drag]` regions, the translucent New-session button,
    the sidebar gradient;
  - the **native keyboard bridge** becomes mandatory: with the mark set, `dsh-client-shortcuts`
    throws `Desktop keyboard bridge unavailable` unless `window.dshDesktop.keyboard` exists, and the
    frame does not mount at all.
- **The native keyboard bridge is real, not a stub.** In desktop runtime the DOM key path serves only
  fixed actions, so the configurable bindings must arrive over IPC. The main process imports the
  harness's own published domain module (`@deepseek-ai/dsh-client-shortcuts/protocol`) to resolve the
  binding table, claims registered chords on `before-input-event`, and delivers them to the page.
  Preferences persist at `<stateDir>/keybindings.json`.
- **Window chrome**: `titleBarStyle: hiddenInset` with `trafficLightPosition {x:16, y:18}`,
  `vibrancy: 'sidebar'` and a transparent background — the official shell's own darwin values. The
  vibrancy matters: under the mark the harness's frame is `background: 0 0` and its sidebar is a
  `color-mix(…, transparent)` gradient, so a native material has to sit behind it.
- **Safety**: the preload marks the document only when the bridge is confirmed live, so if the
  protocol module cannot load the app degrades to the previous behaviour (56px rail, working app)
  rather than a dead boot. The previous session's `rail-collapse.ts` injection stays as the fallback.

## Fixed after the first parity build (same day, founder's eyes)

- **The colour was off.** The native material behind the sidebar followed the OS appearance while the
  app ran its own theme, so a light app on a dark system translated a dark grey panel behind a light
  UI. The shell now mirrors the harness's theme source (`html[data-ds-theme-source]`, `system` |
  `light` | `dark`, written by `ui-layout`) into Electron's `nativeTheme.themeSource`, which fixes the
  material, the window chrome and renderer `prefers-color-scheme` in one step. Fullscreen is mirrored
  the same way, so the harness's 48px title-band clearance and the hidden traffic lights agree.
- **"If I click settings, another menu pops up top left."** Our Muen account overlay (Epic 92) hid the
  stock settings rail and then *clicked the hidden launcher button*. A hidden element measures `0x0`,
  so anything anchored to it opens clamped at the window's top-left. Root cause, read from the
  harness's own source: the `settings.launcher` slot is filled by `AccountMenu` — that launcher **is**
  the account menu's anchor, which is why the stray panel was the account menu (Settings / Feedback /
  Sign in). The overlay now opens Settings through the harness's **command path** instead —
  `{kind:'menu', commandId:'settings.open'}` over the bridge, the same mechanism the official shell
  drives its File menu with — which involves no DOM anchor and no key gesture at all.
