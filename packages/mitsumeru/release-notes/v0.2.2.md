Production build — `latest` channel, like 0.2.0 and 0.2.1. **This release ships three
targets: Apple Silicon, Intel, and Windows x64.**

## Intel and Windows are back, and this time they work

0.1.9-dev's Intel dmg and Windows exe have never started. 0.2.0 and 0.2.1 shipped
arm64 only, by decision, because the alternative was handing out builds that could
not launch. Both facts had the same cause, and it is fixed here.

`prepare-harness.sh` staged the host closure with no platform handling at all, and
electron-builder copies that ONE tree into every target it builds. So the x64 app
and the Windows exe both received Apple Silicon native addons —
`node-addon-require-builtin-darwin-arm64` — and an x86_64 process cannot load arm64
code. Rosetta does not go that direction. The build log had been listing every
platform-specific dependency it could not bundle, in every build:

> `platform-specific optional dependencies not bundled … node-addon-require-builtin-darwin-x64, … win32-x64-msvc, @koromix/koffi-darwin-x64, @vscode/ripgrep-darwin-x64, @img/sharp-darwin-x64 …`

Staging is now per target (`--os` / `--cpu`, writing `supportedArchitectures` into
the stage), and the build is per target too, so what gets packaged is what was
staged:

| Artifact | Architecture |
|---|---|
| `Mitsumeru-0.2.2-arm64.dmg` / `-arm64-mac.zip` | Apple Silicon |
| `Mitsumeru-0.2.2.dmg` / `-mac.zip` | Intel (x86_64) |
| `Mitsumeru Setup 0.2.2.exe` | Windows x64 |

Two further traps had to go, both of which silently produced the wrong build: the
notarize step deleted *every* artifact and repacked from `release/mac-arm64` (that
is how a two-arch release became arm64-only in 0.2.0 and 0.2.1), and the repackage
invocation had no arch flag, so electron-builder packaged for the **host** and
handed back arm64 artifacts for an Intel app. Both are fixed and both are now
asserted rather than trusted.

## Windows is unsigned in this release

`Mitsumeru Setup 0.2.2.exe` carries no Authenticode signature — there is no
Windows code-signing certificate on this rig, and the certificate is a purchase
with identity validation (Azure Artifact Signing is the cheapest path at ~$10/mo;
OV certificates start around $150/yr). Expect **"Windows protected your PC"** on
first run: *More info → Run anyway*. That is the unsigned path behaving as
documented, not a packaging fault.

Worth knowing before buying: **EV certificates stopped bypassing SmartScreen in
2024**, so paying the EV premium for that reason is no longer justified. Any valid
certificate still helps — reputation accumulates against a consistent publisher
identity and carries across releases, while unsigned builds start from zero every
version.

## Gates

- **`pnpm verify:release` — 36 checks, 0 failures**, run once per architecture: both
  apps signed with the Developer ID and carrying a secure timestamp, both dmgs
  accepted by Gatekeeper and stapled, the app **inside** each zip and **inside**
  each dmg carrying a stapled ticket and passing Gatekeeper, and all four
  `latest-mac.yml` entries matching sha512 and size on disk. The gate also fails a
  feed that lists fewer than four artifacts — the shape an Intel client experiences
  as "no update available".
- **`pnpm verify:arch`** — each app's Mach-O architecture, the harness addon it
  must load, and the absence of the *other* architecture's addon; then a real boot
  of the packaged harness on the package's own Electron. The Intel app is booted
  under Rosetta, and it serves its page.
- **`PROMOTE=1 pnpm check:label` — 8/8**, including all four artifacts carrying the
  version and the packaged app reporting it.

## Known, not fixed in this release

- **Windows is unsigned** (above).
- `verify:survives-update` still fails on `@muen/dsh-white-label` importing
  `@deepseek-ai/schemastery` without declaring it, so installing that plugin from
  source cannot resolve it. Carried from 0.2.0; the shipped app is unaffected.
- `@muen/dsh-codex-fold`'s Settings card ("Status text") cannot render on DSH
  0.1.6-alpha.2: `settings.plugin.item` is declared by no bundle. Its folding is
  unaffected.
- **The download page's Windows row stays off until the installer is signed.** The page
  itself is already architecture-aware and deployed (2026-09-18): it picks the Intel dmg
  when the browser reports x86, recommends the matching row, and lists the other
  architecture beside it. One step happens with this publication — the static fallback
  `href` moves from 0.2.1 to 0.2.2, because `verify:distribution` downloads the fallback
  rather than the release the page resolves at load.

## Install

- **Apple Silicon:** `Mitsumeru-0.2.2-arm64.dmg`
- **Intel:** `Mitsumeru-0.2.2.dmg`
- **Windows:** `Mitsumeru-Setup-0.2.2.exe` (unsigned — see above)

macOS builds are notarized and stapled, so they open on a double-click.
`latest-mac.yml` and `latest.yml` are the update manifests and ship beside the binaries.

The `.exe` asset name is hyphenated on purpose: electron-builder writes that name into
`latest.yml`'s `url`, and the Windows updater downloads what the manifest names. The local
build output keeps the space (`Mitsumeru Setup 0.2.2.exe`); only the uploaded asset is
renamed.
