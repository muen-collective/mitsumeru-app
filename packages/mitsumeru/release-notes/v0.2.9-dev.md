# Mitsumeru 0.2.9-dev

Internal build — carries the `-dev` suffix; the update channel is `dev`.

Wraps DeepSeek Harness **0.2.1-rc.5** (from **0.2.1-rc.2**) — the newest release on DSH's `latest`
tag, published 2026-10-29. Nothing in the shell changed: this cut exists to move the harness under
it, and to prove the things that only a real harness can tell us.

## What changed

- **The pin.** `@deepseek-ai/dsh` 0.2.1-rc.2 → **0.2.1-rc.5**, passing through rc.3 (2026-10-23)
  and rc.4 (2026-10-26), which no cut ever wrapped. `0.2.2-alpha.2` was published earlier than
  rc.5 and is the next line's alpha, so `latest` was the channel to follow, as it has been for
  every re-pin since 0.1.5.

- **The closure delta is one package, and it is additive.** 308 `@deepseek-ai/*` packages resolve;
  the only name that was not there before is
  **`@deepseek-ai/dsh-client-ui-entry-customization`** — upstream's description: *"Customize plugin
  entries in the left sidebar, conversation views, and right sidebar, and quickly create new
  plugins."* Nothing was dropped. No module we patch moved.

- **The missing-edge pin still earns its keep.** At rc.5 the renderer still
  `require`s `@deepseek-ai/dsh-client-ui-slots` at module load and still declares no dependency on
  it — so the staging pin of that edge in `prepare-harness.sh` is unchanged, and is still what
  keeps the packaged app from booting to a blank page. (Checked against the staged tree, not
  against memory: `dsh-client-ui-renderer@0.2.1-rc.5` declares it in neither `dependencies` nor
  `peerDependencies`.)

- **Both client patches applied unchanged**: the hero-tagline seam and the `@muen` beta badge.

## What to check

- The app boots and the conversation renders — the re-pin's only real risk is a surface that
  loads but does not paint.
- **The sidebar still wears our dot** (#FF5E00 / #FF0004), not upstream's. The brand seat is the
  one thing that has silently regressed before.
- Upstream's new **entry customization** lives in the plugin settings. It is theirs; nothing of
  ours claims that seat, and nothing of ours needs to.

## The audits the pin requires

- **No plugin calls the removed settings API.** `settings.register` appears nowhere in
  `plugins/*/lib`; `@muen/dsh-white-label` configures through `configure(`, the shape rc.5 still
  expects.
- **Upstream's composition patch changed by one row.** Diffing `dsh-web-app/cordis.patch.yml`
  between rc.2 (the tree 0.2.8 shipped) and rc.5 gives exactly the new `entry-customization` row and
  no new `!!js` gate — nothing vanished behind a profile-name condition this time.
- **Every bundle upstream declares still resolves.** All 15 `@deepseek-ai/*` bundles referenced by
  the `mitsu` profile exist in the rc.5 closure, and every `@muen/*` link is present.

## One plugin is skipped on rc.5, and it is not ours

`dsh-codex-connect@0.2.0-alpha.10` declares support up to `0.2.1-rc.3` and stops there, so rc.5
refuses it and the boot log carries exactly one line:

```
dsh: skipping profile bundle "dsh-codex-connect"
  Plugin dsh-codex-connect@0.2.0-alpha.10 is incompatible with dsh 0.2.1-rc.5
```

It is non-fatal — the app boots, everything else mounts, and the harness only loses that one
bundle. It is also the breakage class a package-existence audit cannot see, because nothing is
missing: the plugin's own version range is what rejects the runtime. Two honest options, neither
taken here: a newer `dsh-codex-connect`, or an explicit exact-version exemption
(`dsh plugin allow-version`, or the plugin manager's UI) — a deliberate risk decision about running
a plugin upstream has not blessed against this runtime.

## Windows

Unsigned, as the supported path: the installer carries the win32-x64 payload and its update feed,
and unsigned auto-update works because `app-update.yml` names no publisher. When published it must
use the hyphenated copy (`Mitsumeru-Setup-0.2.9-dev.exe`) that `latest.yml`/`dev.yml` name, the way
0.2.8 did.
