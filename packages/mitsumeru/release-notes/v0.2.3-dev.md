Internal build — carries the `-dev` suffix; the update channel it belongs to is
`dev`.

**The brand now travels inside the build.** Until now a white-label brand lived
only in runtime state, so installing a new core looked exactly like losing it:
the tagline, the status label, the accent and the marks were gone, and re-adding
them by hand did not survive the next launch either. The cause was an upstream
API change, not the plugin's logic.

DSH 0.1.6-alpha.2 exposed `settings.register(namespace, schema, { base })`, and
`@muen/dsh-white-label` used it. **0.1.7-rc.1 removed it** — the settings service
now exposes `configure`, `describe`, `update`, `replace` and `mutate`, and
nothing else. The call threw `register is not a function` into the `catch` that
had been there to tolerate a namespace someone else had already taken, so it
failed silently: nothing logged, the namespace never resolved, and persistence
fell back to the browser's `localStorage` mirror. That mirror is not durable —
the harness serves a fresh port on every launch and `localStorage` is
origin-scoped — so the brand was wiped by the next start.

0.1.7 also replaced that API with a better one, and the plugin now uses it: **a
plugin's durable namespace is its own profile entry id**, and its Config is the
namespace, projected to the browser when it carries `volatile()` fields. So the
brand is not copied into a state directory and it is not baked into a client
bundle. It is **config in the layer that belongs to the build** — the plugin's
own bundle patch — and the patch layer order does the rest:

| Layer | Holds | Outranks |
|---|---|---|
| the plugin's bundle patch | the brand this build ships | — |
| the profile's `cordis.patch.yml` | what a person saved in Settings → Brand | the build's brand |
| `$DSH_HOME/cordis.patch.yml` | an operator's machine-wide override | both |

The consequence is the one that matters for release: **a brand someone saves
survives an app update**, and Reset restores the shipped values.

**Ship or change the brand from one file.** `build/brand/white-label/brand.json`
plus the PNGs beside it are the whole input, and `scripts/apply-white-label-brand.mjs`
folds them into the vendored plugin's patch during the build (`prepare-harness.sh`
runs it after vendoring, so it always writes onto a fresh copy). Delete that
folder and the build ships the plugin's neutral defaults — no build carries an
identity it was not given. This build ships the authored brand: the tagline, the
run-status label, the light accent, and the light/dark wordmark pair.

**The accent is durable too.** It had the same failure mode, and it rides the
same document now — keeping it in `localStorage` alone would have reproduced the
loss for anyone who picked a colour.

**A duplicate Brand page is suppressed.** A schema with `volatile()` fields
auto-generates a Settings page, and `auto` defaults to true, so declaring the
Config would have put the brand on a second, generated page as well as the
plugin's own. The plugin registers `configure({ auto: false }, ctx.fiber)` as an
effect, per the `dsh-settings` README rule for a plugin that ships its own page.

**A new harness underneath: DeepSeek Harness 0.1.7-rc.1**, up from
0.1.6-alpha.2.

**The Sidebar Browser tab is off by default, and that is upstream's choice.**
0.1.6-alpha.2 composed `ui-sidebar-browser` unconditionally. 0.1.7-rc.1 keeps the
package — `@deepseek-ai/dsh-client-ui-sidebar-browser`, "Sandboxed Web browser
tabs for the right Sidebar" — but gates the row on the profile being named
`desktop`:

```yaml
# Web profiles opt in; Desktop retains sandboxed HTTP(S) Browser tabs.
- id: ui-sidebar-browser
  name: '@deepseek-ai/dsh-client-ui-sidebar-browser'
  disabled: !!js "ctx.get('profileContext')?.name !== 'desktop'"
```

This app's profile is named `mitsu`, so the gate never passes and the tab
vanishes — it is not removed, and nothing in this repo disabled it. To opt back
in, override the row by id in the profile's `cordis.patch.yml`:

```yaml
- id: ui-sidebar-browser
  disabled: false
```

That is verified in a throwaway profile: the row composes with `disabled: false`
and the plugin reaches the DOM. One thing to know before enabling it: `dsh-base`
gates `desktopPlatform` (the DeepSeek account's desktop handoff) on the SAME
profile name, but wraps it in a fallback, so a browser-only override is safe —
while **renaming the profile to `desktop` would also switch the account plugin
into its desktop mode**, which is a different decision than re-enabling a tab.
The override-by-id route changes exactly one thing.

### Verified on this build

- `node --test tests/*.test.mjs` in `muen-plugins` — 47 pass, including three new
  cases pinning this contract: the namespace is the entry id and not the old
  name, the 0.1.6 `register` call is capability-guarded rather than left to
  throw, and the accent writes through to the durable document.
- `--dump-config` on a throwaway profile with an **empty** profile patch: the
  brand arrives from the bundle layer (`brandTagline`, `statusLabel`, `accentLight`,
  and both logos), and a row added to the profile layer replaces it.
- The **packaged** app, in a fresh profile with empty `localStorage` and an empty
  profile patch: Settings → Brand reads back the shipped tagline and status label,
  and all seven brand marks render.
- The shipped accent is live, read off the running app rather than the schema:
  `--dsw-alias-brand-primary: #4f83f2` and its derived
  `--dsw-alias-button-primary-hover: #6f99f4`.
- `scripts/white-label-probe.cjs` against the packaged harness: PASS.
- Both architectures are notarized and stapled, and the full release gate passes
  for each: `Mitsumeru-0.2.3-dev.dmg` + `-mac.zip` (Intel) and
  `Mitsumeru-0.2.3-dev-arm64.dmg` + `-arm64-mac.zip` (Apple Silicon). Gatekeeper
  accepts the dmg, the zip, and the app inside each; every Mach-O binary in the
  harness tree is signed; `verify:arch` boots both and confirms neither carries
  the other's native addon.

Merging the feed for the first time caught a second bug, in `manifest:merge`: it
concatenated whatever fragments were in `release/`, so this build's
`dev-mac.yml` claimed `version: 0.2.3-dev` while listing the **0.2.2** Intel zip
and dmg — which an Intel client would have downloaded and installed as
"0.2.3-dev". Fragments from another version are now dropped, loudly, and a feed
with no entry for the current version fails instead of shipping. The same merge
is what makes a one-arch release visible: it warns when fewer than two artifacts
are present rather than quietly publishing a feed that strands a platform.

Fixing the accent check turned up a flaw in the probe itself: it read the token
from `documentElement`, while the plugin's theme override lands on `<body>`, so it
reported "default" for a build whose accent was applied. It reads `<body>` now —
the accent is the one part of the brand a screenshot cannot confirm, and a false
negative on it is exactly the kind of result that sends you re-checking a correct
change.

### Known, and deliberate

A hand-written row in the profile's `cordis.patch.yml` **replaces** the whole
config object instead of merging field by field, so a row that sets only
`brandTagline` drops the shipped marks. The Settings UI is unaffected — it writes
the full resolved config, and Reset deletes the row and brings the build's values
back.
