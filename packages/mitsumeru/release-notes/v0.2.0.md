Production build — the `-dev` suffix comes off for this one, so it leaves the `dev`
channel: the update manifest it writes is `latest-mac.yml`, not `dev-mac.yml`, and
the version-label gate runs in promotion mode (`PROMOTE=1 pnpm check:label`).

**This release is arm64-only, and that is a decision rather than an omission.** The
Intel (x64) and Windows targets are not shipped because they cannot work as built:
`prepare-harness.sh` stages the host closure and has no platform handling at all, so
every target receives Apple Silicon native addons. The x64 app's
`node-addon-require-builtin-darwin-arm64/prebuilt/darwin-arm64-napi-v9.node` is a
Mach-O **arm64** bundle, and the loader resolves its prebuilt from
`${process.platform}-${process.arch}` — on Intel it asks for `darwin-x64` and finds
nothing. An x86_64 process cannot load arm64 code, and Rosetta does not go that
direction. electron-builder had said so in every build log
(`node-addon-require-builtin-darwin-x64@0.1.6` under "platform-specific optional
dependencies not bundled"); the warning had simply never been connected to the Intel
target. This is not new to 0.2.0 — 0.1.9-dev's Intel dmg and Windows exe carry the
same defect, so neither has ever worked. `latest-mac.yml` lists only the arm64
artifacts, so an Intel client finds no suitable file and stays where it is instead of
being handed a build that will not start.

**Copy buttons work.** Every Copy control in the app — code blocks, tool results,
diffs, terminal output — was a click that did nothing. The cause was ours, in the
shell, not in the harness UI: the app installed a lockdown permission handler
that denied **every** permission request, and Chromium asks for
`clipboard-sanitized-write` before the async Clipboard API will write. The
harness's own copy helper catches that rejection and returns false, and its
caller returns early on false — so the button neither wrote to the clipboard nor
showed its "Copied" state. There was no error to see, because the failure path
was designed to be silent.

The fix keeps the posture and names one exception: `clipboard-sanitized-write` is
allowed, on both of Electron's permission paths (the check handler and the
request handler — the docs are explicit that most web APIs check first and
request only if the check is denied), and everything else stays denied and
logged. `clipboard-read` is deliberately **not** allowed: nothing in the UI reads
the clipboard through the async API (the terminal's paste path goes through DOM
paste events, which need no permission), and allowing it would let any page in
the harness origin read whatever was last copied.

Two things this does not fix, both upstream: the copy control has no hover or
active style of its own (only `cursor: pointer`), and a failed write still gives
no feedback. Worth raising upstream rather than patching here.

**The hero tagline is part of the brand now, and it ships.** The blank-session
headline above the composer ("Into the Unknown" / 探索未至之境) is brand copy, so
`@muen/dsh-white-label` owns it: **Settings → Brand → Hero tagline**, up to 200
characters, persisted as `brandTagline` in the durable `white-label-brand`
namespace. Empty keeps the shipped headline — the occupant re-renders the copy
the harness hands it as `fallbackText`, so the words never vanish while a brand
is being edited.

The headline has no slot and a plugin cannot declare one (slot names live in the
compiled render tree, and a parent factory must declare a child before any
renderer may call it), so the seat is a narrow additive patch to the vendored
client bundle. It is **two** edits, and this is measured rather than assumed: the
`renderSlot("conversation.hero.tagline", …)` call in `HeroShell` **and** the seat's
declaration in the `conversation.content` factory's `children` table. The call
without the declaration was shipped to this machine on 2026-09-17 and blanked
every new session — no hero, no composer — because `boundFactoryRenderSlot`
throws `SlotOwnershipError` during render and takes the whole view with it.

**The build patches; packaging no longer does.** The seam is applied by
`prepare-harness.sh` to the staged harness, **before** electron-builder signs and
packages the app, so the edit is inside the code signature. The previous route —
running the patch script against an installed app — cost the signature
(`codesign --verify`: "a sealed resource is missing or invalid", naming the edited
file and the `.muen-unpatched` sidecar the field script leaves beside it) and left
Gatekeeper unable to assess the app. The staged path passes `--no-backup`, so no
sidecar is packaged, and it runs `verify-hero-tagline` as a build gate that fails
on an unpatched bundle **and** on the A-only shape above.

**white-label is the current plugin again.** The vendored copy inside the app was
a version behind its source: no tagline, no WebP, no two-seat split. It is now
synced with `muen-plugins` (all five files byte-identical), and its README
documents the two mark seats, the validation rules, the brand folder, and the
tagline — including that the seam ships from 0.2.0 and is inert on a stock DSH
install, where a save now says so instead of looking broken. The plugin's
user-facing strings no longer tell a client to run a script out of the Muen repo.

Wraps DeepSeek Harness 0.1.6-alpha.2 and Electron 44.0.0 — both unchanged from
0.1.9-dev. macOS `arm64` only; see the first section for why x64 and Windows are
not here.
